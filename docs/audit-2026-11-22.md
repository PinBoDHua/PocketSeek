# PocketSeek 前后端代码审计报告

- 审计日期：2026-11-22
- 审计基线版本：`0.6.0`（`master`，最近提交 `795a8ce`）；高危修复版本：`0.6.1`；中危修复版本：`0.6.2`
- 审计对象：`src/` Web 前端、`android/` Capacitor 原生壳、API 集成层、构建/部署/测试配置
- 审计方式：静态代码审阅 + 构建/类型/lint 门禁 + 依赖漏洞审计 + 发布包校验 + 密钥泄露扫描
- 说明：本项目没有传统服务端，"后端"指 DeepSeek API 集成层（`src/services/api`）、Android 原生插件与本地开发服务器（`scripts/`）。

---

## 1. 结论摘要

整体工程化水平较好：TypeScript `strict` 全开、oxlint 零告警、生产构建通过、CI 使用固定 SHA 的 Action 且权限最小化；Markdown 原始 HTML 按文本渲染、导入 ZIP 做了较严格的路径穿越与 CRC 校验、API Key 只走请求头且未发现硬编码密钥。

但仍有需要优先处理的问题，集中在四类：

1. **模型输出渲染链的已知漏洞**：Mermaid 11.10.1 / KaTeX 0.16.22 / 传递依赖 lodash-es 命中 12 条生产依赖告警（1 高危、9 中危、2 低危），Mermaid 生成的 SVG 被直接 `dangerouslySetInnerHTML` 注入页面，且 `themeCSS` 指令可注入全局样式；同时缺少 CSP。
2. **密钥与隐私边界**：API Key 明文存放在 WebView `localStorage`，Android 又开启了 `allowBackup`，云备份/任何 XSS 都可能带走 Key；后端 Files API 上传的附件在删除会话后不会删除，且签名口令以硬编码默认值 + 文档公开。
3. **原生入口与导入链的资源上限缺失**：导出 Activity 接受任意应用分享，文本内容无大小/条数上限；历史 ZIP 导入无业务大小上限，存在解压炸弹/内存耗尽风险。
4. **本地持久化与备份完整性**：发送后先清草稿再异步落盘、附件与会话同事务写入、导出仅含图片且导入清空原件——这三处都可能造成不可恢复的数据丢失；此外还有系统性的键盘/读屏无障碍缺口与流式渲染性能问题。

按严重度统计（按问题 ID，详见第 4 节）：**高危 7 项、中危 33 项、低危 10 项，共 50 个条目**（部分相邻低危条目已合并叙述）。

> 2026-11-22 已完成 7 项高危问题的修复（见第 9 节，0.6.1）；33 项中危问题已全部修复并随 0.6.2 发布（SEC-22/23 随高危批次完成；第 10、11 节各 10 项，第 12 节为剩余 11 项）。

## 5. 详细问题

### SEC-01（高）模型输出中的 Mermaid/KaTeX 依赖漏洞与 SVG 注入

**位置**

- `package.json:29`（`katex 0.16.22`）、`package.json:34`（`mermaid 11.10.1`）
- `src/services/markdown/mermaid.ts:36-44`（`securityLevel: 'strict'`，直接 `mermaid.render`）
- `src/components/markdown/MermaidDiagram.tsx:91`（`dangerouslySetInnerHTML={{ __html: result.svg }}`）
- `src/components/markdown/CodeBlock.tsx:171`、`src/components/markdown/MathFormula.tsx:56,66`（其他 `dangerouslySetInnerHTML`）

**证据**

`pnpm audit --prod` 输出 12 个生产依赖告警：1 个 high（`lodash-es` 经 `mermaid` 引入的代码注入）、9 个 moderate（Mermaid `classDef`/配置 CSS 注入、Gantt/XY/radar 无限循环 DoS、prototype pollution 等）、2 个 low（Mermaid 配置原型污染、KaTeX 原型污染绕过 trust）。漏洞修复版本为 `mermaid >= 11.16.1`、`katex >= 0.18.2`、`lodash-es >= 4.17.24`。

Mermaid 渲染的是模型输出的任意文本，渲染结果 SVG 未做额外净化即注入页面；`sanitizeMermaid` 只用正则转义 `<img`/`<image` 标签（`mermaid.ts:17-18`），不能抵御上述 CSS/HTML 注入类问题。页面也没有 CSP（`src/index.html` 无 CSP meta），一旦注入成功，页面同源脚本可读取 `localStorage` 中的 API Key。

此外，Mermaid 指令中的 `themeCSS` 不在 `securityLevel: 'strict'` 的 secure 白名单内，会被拼进 SVG 内的 `<style>`，随 `dangerouslySetInnerHTML` 注入主文档（`MermaidDiagram.tsx:91`），形成**全局 CSS 注入**：可遮挡/伪造界面，并通过 `@import url(https://…)` 外带 IP 与追踪。这不是理论问题，属于 Mermaid 11.10.1 已公开的 CSS 注入缺陷族。

**影响**

恶意或被污染的模型输出（以及联网搜索返回内容被模型转述后）可在聊天 DOM 内注入样式/HTML，造成界面劫持、信息泄露（配合 SEC-02 可窃取 API Key）、DoS（特定图表死循环）。当前 `securityLevel: 'strict'` 降低了风险，但不能覆盖所有已披露问题。

**建议**

1. 升级并锁定：`mermaid >= 11.16.1`、`katex >= 0.18.2`，用 `pnpm.overrides` 将 `lodash-es` 提到 `>=4.17.24`。
2. 对最终 SVG 再做一次白名单净化（如 DOMPurify 的 SVG profile）或放入 `sandbox` iframe 渲染。
3. 增加 CSP：至少 `script-src 'self'`，并限制 `img-src`/`style-src`；GitHub Pages 无法设响应头，可用 `<meta http-equiv="Content-Security-Policy">`。
4. 限制单张 Mermaid 图的源码长度/节点数，避免渲染 DoS。

### SEC-02（高）API Key 明文 localStorage + Android 允许备份

**位置**

- `src/services/settings.ts:41-54`（`pocketseek:api-key`）、`settings.ts:121-122`（初始化读取）、`settings.ts:157-160`（写入）
- `src/services/api/client.ts:86-100`（Key 通过请求头发送）
- `android/app/src/main/AndroidManifest.xml:5`（`android:allowBackup="true"`，无 `fullBackupContent`/`dataExtractionRules`）

**证据**

API Key 以明文写入 WebView 的 `localStorage`。Android 默认备份会把应用私有目录（含 WebView 的 Local Storage/IndexedDB）纳入云备份或设备迁移；仓库中没有备份排除规则。README 对外表述为"API Key 只保存在你自己的浏览器里"（`README.md:10`），但云备份场景下该承诺不成立。

**影响**

- 任意 XSS（SEC-01）或恶意导入内容 + 点击可读取 Key，直接造成账户费用损失。
- 设备云备份/换机迁移会把 Key 带到用户未预期的位置；`adb backup`（旧系统）也可能导出。
- 应用无 Key 加密或访问控制，Root/调试设备可直接读取。

**建议**

1. 原生侧新增安全存储插件：Android Keystore + `EncryptedSharedPreferences`（或 `EncryptedFile`），Web 层通过 Capacitor 插件读写，不再落 `localStorage`。
2. `allowBackup` 改为 `false`，或至少提供 `dataExtractionRules`/`fullBackupContent` 排除 WebView 数据与 Key。
3. 增加 CSP 与输出净化，降低 XSS 读取面（与 SEC-01 联动）。
4. 文档补充"Key 的存储位置与备份行为"。

### SEC-03（中）原生分享入口文本无上限，任意应用可触发

**位置**

- `android/app/src/main/java/com/pocketseek/app/ShareReceiverPlugin.java:36-38`（静态 `PENDING_TEXTS`/`PENDING_URIS`）
- 同文件 `:113-131`（`capture` 累加文本，无长度/条数限制）、`:134-152`（`extractText` 直接 `toString().trim()`）
- `AndroidManifest.xml:26-40`（`MainActivity` 导出并接收 `SEND`/`SEND_MULTIPLE`）

**证据**

任何应用都可以向该 Activity 发送 `ACTION_SEND`。`capture` 对 `EXTRA_TEXT`/`ClipData` 文本不设上限，且每次分享都会向静态列表追加；若 JS 侧未及时 `getPending`（WebView 未加载/后台挂起/崩溃），列表会持续增长。图片虽有单张 12MB、总量 24MB 上限（`:31-33`、`:75-95`），但会整体 Base64 编码为约 32MB 字符串跨桥传给 JS，再在 Web 侧 `atob` 解码，低端机存在明显 OOM 风险。

**影响**

恶意应用可反复分享超长文本/大量条目造成内存耗尽、ANR 或崩溃；正常用户分享超大图片也可能触发 OOM。

**建议**

- 文本上限（如 100KB/条、队列总上限 1MB、最多 N 条），超限截断并提示。
- 图片改为传递 `content://` URI/临时文件路径，由 JS 按需读取；或降低总预算并在后台线程分块读取。
- 对 `PENDING_*` 队列做容量控制（丢弃最旧或拒绝新条目）。

### SEC-04（中）删除会话不清理远端 Files API 文件

**位置**

- `src/services/api/client.ts:102-104`（上传文件"不设过期时间"）
- `src/services/api/client.ts:126-132`（`deleteFile` 已实现）
- `src/services/chat/db.ts:130`（注释明确"远端文件不删"）、`:140-143`（只删本地无引用原件）
- 全仓库检索：`deleteFile` 无调用点

**证据**

附件上传到 Files API 后永久保留；用户删除消息/会话时只清 IndexedDB 本地副本。`deleteFile` 从未被调用，也没有"清理云端文件"的入口。

**影响**

- 用户以为删除的文档/图片仍留在服务端，隐私删除不彻底。
- Files API 有文件数与存储配额（`errors.ts:97-115` 已处理配额错误），长期使用会因孤儿文件提前触顶。

**建议**

- 删除会话/消息时统计不再被任何本地会话引用的 `serverId`，后台串行调用 `deleteFile`（需处理失败与重试）。
- 或在设置中提供"清理云端附件"功能，并明确保留策略。
- 注意：删除远端文件会使其他设备/导出归档中的旧附件失效，需在产品层说明。

**位置**

- `android/app/build.gradle:19-27`（原实现：环境变量缺失时回退到可预测的硬编码默认口令；0.6.1 后已移除）

### SEC-07（高）历史 ZIP 导入无业务大小上限

**位置**

- `src/services/chat/history/README.md:61`（明确"不另设业务大小上限"）
- `src/services/chat/history/zipReader.ts:241-299`（按条目流式解压，仅校验声明大小与 CRC）
- `src/services/chat/history/importArchive.ts:45,98`（`readEntry` 把整个条目读成 Blob/文本）

**证据**

ZIP 解析对路径穿越、ZIP64、加密、CRC、声明大小与实际输出不一致等做了严格校验（这部分实现良好），但没有对单条目/整包解压后大小、条目数、会话数设置上限。攻击者可构造高压缩比 ZIP（声明解压大小接近 4GB 且 CRC 正确），导入时 `readEntry` 会把整个条目累积为 Blob/字符串；`importArchive.ts:44-51,93-101` 随后整串 `JSON.parse`、整图写库。几 MB 的炸弹 ZIP 即可产生数 GB 内存并撑爆存储配额，导致 OOM、导入失败，且条目数最多可达 65534。

**影响**

用户导入来源不明的"历史归档"时可能被 DoS；若导入流程在写入正式库前崩溃，原数据尚能保留（暂存区设计正确），但体验与信任受损。

**建议**

- 设置业务上限：单条目（如 32MB）、整包解压总量（如 512MB）、条目数/会话数/图片数上限。
- 对会话 JSON 使用大小预检（`entry.size`）后再 `readEntry`。

### SEC-21（中）本地静态服务器路径越界与崩溃风险

**位置**

- `scripts/serve.mjs:13`（默认 `HOST=0.0.0.0`，面向局域网）
- `scripts/serve.mjs:32`（`decodeURIComponent` 在 try 之外，畸形 `%` 可抛未捕获异常）
- `scripts/serve.mjs:36-40`（`filePath.startsWith(root)` 未带路径分隔符）
- `scripts/serve.mjs:45`（`filePath.includes('static')` 决定一年缓存）
- `scripts/serve.mjs:48-52`（任何读取失败都回退 `index.html` 并返回 200）

**证据**

拼接后的路径用 `startsWith(root)` 判断是否在根内，缺少分隔符：同级的 `dist-backup/`、`dist2/` 均满足前缀，构造 `/%2e%2e/dist-backup/...` 可读取 dist 之外的兄弟目录。缺失的 `.js` 也会返回 `index.html` 200，浏览器按 JS 解析失败；服务被 `0.0.0.0` 暴露到局域网，任何同网设备均可访问。畸形百分号编码会让 `decodeURIComponent` 抛错，async 请求回调没有捕获，Node 进程可能因未处理拒绝退出。

**影响**

**建议**

- 将 `decodeURIComponent` 放入 try；只对 `/static/` 前缀设置长缓存。

### DATA-01（高）发送后先清草稿、异步落盘，存在消息丢失窗口

**位置**

- `src/services/chat/store.ts:687-688`（先 `persist(sessionId)` 异步写库，随即同步 `clearSentDraft`）
- `src/services/chat/store.ts:215-251`（`persist` 是 fire-and-forget，失败只标记 `sessionSaveErrors`）
- `src/services/chat/drafts.ts:201-203`（`clearSentDraft` 立即清空内存草稿并删除 localStorage 草稿）
- `src/services/chat/store.ts:1240-1251`（启动补发时若会话不存在，直接删除 outbox 条目）

**证据**

在线发送时没有 outbox 兜底：消息先进入内存会话，`persist` 尚未完成就清空草稿。若 IndexedDB 写入失败（配额、连接关闭）或进程在大附件写入期间被杀，重启后该会话不存在或缺少这条消息，而文字草稿也已被删除，且没有队列可恢复。

**建议**

- 草稿清理延迟到 `saveSession` 成功回调；或在清除前保留一份"待确认草稿"，失败时恢复。
- 在线发送也先落一条轻量 outbox/事务日志，持久化成功后再标记完成。
- 为发送流程增加端到端失败注入测试。

**证据**

**影响**

**建议**

- 附件 Blob 独立存储并单独失败，会话文本优先持久化。
- 写入前用 `navigator.storage.estimate()` 估算配额并提示清理。
- 限制单消息附件总大小（如 100MB），而不是仅限制个数。

**位置**

## 6. 已确认的良好实践

- Markdown 原始 HTML 不会被当作 HTML 执行：`MarkdownAstRenderer.tsx:16-21,122-123,178-179` 以文本节点渲染。
- Markdown 链接只允许 http/https/mailto：`Link.tsx:4-19`。
- 代码高亮使用 Prism 转义输出（`CodeBlock.tsx:151`）；KaTeX 未启用 `trust`，`\href`/`\html*` 不生效（`MathFormula.tsx:38`）；Mermaid 设置了 `securityLevel: 'strict'`（`mermaid.ts:38`）——这些是有效的第一层缓解，但不能覆盖旧版本已知缺陷。
- 原生壳跳过 Service Worker（`pwa.ts:80`），避免 WebView 内缓存旧资源；API 为跨域请求，不经 SW 缓存。
- 生产构建 `devtool: false`，`dist/` 无 source map（`rspack.config.ts:44`）。
- ZIP 解析对路径穿越、绝对路径、反斜杠、ZIP64/加密/分卷、CRC 与声明大小做了严格校验：`zipReader.ts:61-75,140-152,180-229`。
- API Key 只放在请求头（`Authorization` / `x-api-key`），未拼接到 URL：`client.ts:86-100`。
- Store 在 `visibilitychange`/`pagehide` 时冲刷未保存增量，保存失败会记录 `sessionSaveErrors` 并在 UI 提供重试（`store.ts:215-287`）。
- CI 使用固定 commit SHA 的 Actions，权限最小化（`contents: read`、`pages: write` 仅部署 job）：`pages.yml`。
- 无源码映射泄漏；APK sha256 可验证；无硬编码 API Key。
